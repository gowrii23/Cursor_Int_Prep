Colibri: a 744B MoE model on a 25 GB laptop

Colibri (JustVugg, Apache 2.0, released July 2026) is a pure-C inference engine for GLM-5.2. It never loads the whole model: the always-used parts live in RAM and the experts stream from an NVMe SSD on demand. Goal of this note: learn the basics well enough to explain it in an interview and build a mini version.

The one idea everything rests on: in a Mixture-of-Experts model only ~5.4% of the weights (~40B of 744B) compute per token, and only ~11 GB of experts change from one token to the next. So RAM only has to hold the dense part; the disk serves the rest.

🧠 "Few experts work, most sleep on disk; cache the busy, predict the next." Sparsity → streaming → LRU → prefetch.

2. How the router picks experts (toy numbers)

GLM-5.2 uses a DeepSeek-V3-style sigmoid router with a shared expert. Toy layer: 8 experts, top-k = 2. (Real models are much bigger; DeepSeek-V3 uses 256 routed + 1 shared, top-8. GLM-5.2's exact k is not in the sources I used.)

  1. Score: one small matrix W (experts × hidden) times the token's hidden state h, then sigmoid. Each expert gets an independent 0–1 affinity (no softmax competition).
  2. Bias picks: a learned per-expert bias nudges under-used experts up, which balances load without an auxiliary loss. E5 jumps from 0.40 to 0.80 and beats E4.
  3. Top-k: keep E1 and E5. The other 6 are never touched, which is why they can sleep on disk.
  4. Raw scores weight: weights use the original scores. Total = 0.91 + 0.40 = 1.31, so E1 = 0.91 / 1.31 ≈ 0.69 and E5 = 0.40 / 1.31 ≈ 0.31.
  5. Shared expert always runs: out = shared(h) + 0.69·E1(h) + 0.31·E5(h). The shared expert is part of the resident dense block.

🧠 "Sigmoid scores, bias picks, raw weights mix, shared always sits."

Java analogy: the router is a PriorityQueue top-k; the expert store is a Caffeine cache over a slow remote store; prefetch is cache warming from a predicted access pattern.

Layer 0 expert usage (orange = currently in its LRU cache):

  1. Set slots to 0: every routed expert is a disk read (4 × 8 × 19 MB ≈ 608 MB/token). Disk time explodes, which is the "naive streaming" baseline.
  2. Raise slots: hit rate climbs fast at first, then flattens. That's the long-tail shape of expert popularity.
  3. Lower skew toward 0 (uniform routing): caching barely helps. Colibri works because real routing is not uniform.
  4. Turn on prefetch: the same misses still read the disk, but most reads overlap with compute, so the stall time drops.

Say it in an interview

  1. MoE makes compute sparse, so memory, not FLOPs, is the real constraint. Colibri turns the memory problem into a caching problem.
  2. Treat VRAM, RAM and NVMe as one hierarchy: resident dense weights, per-layer LRU of hot experts, OS page cache as L2, SSD as backing store.
  3. Hide latency with prediction (router-lookahead, async readahead) and amortize it with speculation (MTP drafts several tokens per pass).
  4. The trade-off is explicit: speed for accessibility. It suits batch work, patient agents, and private/offline use, not snappy chat.
  5. Correctness first: token-exact validation against a reference implementation before any optimization.
